# Batch vs. replay consistency check

**Result: 9/10 argmax matches, max |Δp| = 0.0254** (tolerance: argmax equality + `max_abs_diff < 0.02`).

Run: `uv run python -m scripts.consistency_check --clips results/demo_clips.json` against
`results/stage2_fusion_faces_only/seed1/test_predictions.jsonl` (the batch path) and the
replay path (`TurnProcessor` over the real curated clips' raw video). Raw per-clip output:
`results/consistency_check.json`.

## The two clips outside tolerance

- **`dia65_utt3`** — argmax matches (neutral both sides); `max_abs_diff = 0.0254`, just over
  the 0.02 bound.
- **`dia153_utt4`** — argmax flips on a near-exact tie: batch top = fear (0.328) vs. anger
  (0.318, 2nd); replay top = anger (0.331) vs. fear (0.317, 2nd).

## Root cause (confirmed, not a code defect)

Two real, independently-confirmed asymmetries between how the two sets of numbers were produced,
traced through the actual pipeline code rather than assumed:

1. **Lossy JPEG round-trip.** The batch path's face crops were saved to disk during
   preprocessing via `cv2.imwrite(..., crop)` (`src/meld_emotion/data/preprocess.py`, default
   JPEG quality, no explicit quality parameter) and read back for training/eval. The replay
   path encodes crops directly from decoded video frames in memory — no JPEG step at all. This
   is a real, if usually small, source of drift.
2. **Cross-hardware, cross-precision mismatch (the larger contributor).** `test_predictions.jsonl`
   was generated by the Stage 2 `--eval-test` run on Modal: `results/stage2_fusion_faces_only/seed1/results.json`
   records `"device": "cuda"` and `config.amp_bf16 = true`, i.e. the batch predictions were
   computed on a CUDA GPU under bf16 autocast. The replay path runs on this Mac, which has no
   CUDA — `resolve_device("auto")` resolves to `"mps"`, and inference runs full fp32 with no
   mixed precision. Different hardware, different numeric precision, and different low-level
   kernel implementations (matmul/attention/layernorm) for CUDA vs. MPS are a well-documented
   source of multi-percent-level probability drift in transformer stacks, entirely independent
   of any pipeline bug.

Both mechanisms were checked against the actual code (not asserted): the JPEG asymmetry via a
direct read of `preprocess.py`'s crop-saving code, and the precision/device mismatch via a
direct read of the stored checkpoint's training config. No other asymmetry was found — frame
sampling (`sample_frame_indices`, including the 15s decode cap), face-detector threshold, the
per-clip face-count cap (`subsample_faces`), and track-ID handling are all verified identical
and deterministic between the two paths.

## Disposition

Decision (2026-09-13): **keep as a documented limitation.** The consistency-check code and its
`0.02` tolerance are unchanged — the script is working as designed (it is supposed to catch
exactly this kind of discrepancy, and it did). 9/10 exact matches with a well-understood,
non-structural cause for the other 2 is a defensible result to report as-is, rather than either
loosening the tolerance to paper over real cross-hardware drift or spending time re-computing
`test_predictions.jsonl` locally on MPS/fp32 for a strict apples-to-apples comparison (the
demo's own local inference is what actually matters for the live/replay experience; the batch
number is a training-time artifact from a different, faster piece of hardware).
